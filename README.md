# Moodle LTI: RAG-рекомендательная система интернет-магазина

Внешний тренажёр для лабораторной «Три задания»: LTI 1.3 запуск, проверка ответов на сервере и передача 0–10 баллов в существующую колонку Moodle через AGS. Это **не SCORM ZIP**: Node.js-приложение работает отдельно от LMS.

Репозиторий: [WhoamiTitle/moodle-lti-rag-lab](https://github.com/WhoamiTitle/moodle-lti-rag-lab).

Материалы для сдачи: [единый отчёт](docs/submission-report.md), [план защиты](docs/defense.md), [актуальный результат 63/63 тестов](docs/test-results.json). На публичном Gnomio подтверждены разные оценки **student1 = 10 / student2 = 0** в одной колонке; [настоящий журнал](docs/screenshots/gnomio-gradebook-final-10-0.jpg). Актуальные исходники, инструкции и протоколы находятся в этом репозитории. Архив для сдачи подготовлен отдельно, без секретов.

## Быстрый запуск без Moodle и MongoDB

Нужен Node.js 24+ и Make. Из каталога проекта:

```sh
make install
make test
make demo
```

Откройте [локальный стенд](http://127.0.0.1:3001). Выберите «Студент A», «Студент B» или «Преподаватель». Запуск проходит через настоящий `ltijs`, подписанный RSA JWT, OIDC state/nonce, OAuth client assertion и AGS HTTP-запрос. **Платформа, участники и журнал тестовые; в Gnomio ничего не отправляется.** Демо игнорирует `.env`, слушает только `127.0.0.1` и не заменяет платформу в обычном сервере.

Проверьте 0 баллов (все ответы пустые), 7 (`RAG`, неверный второй, `API`) и 10 (`RAG`, `embedding`, `API`). Для следующего результата нажимайте «Новая попытка». [Тестовый журнал в JSON](http://127.0.0.1:3001/demo/grades) показывает последнюю оценку отдельно для каждого ученика. У преподавателя отправка запрещена.

На главной странице тестовой платформы есть кнопка сбоя следующего AGS-запроса. После сбоя результат станет `pending`; на форме появится «Повторить доставку оценки». Баллы не пересчитываются в другую попытку. После успешного повтора статус — `sent`.

Остановка: `Ctrl+C`. История демонстрации хранится в `data/demo/`, LTI-ключи и тестовый журнал — в памяти. После перезапуска нужен новый запуск элемента; тестовый журнал будет пуст до следующей доставки. Для других портов:

```sh
DEMO_TOOL_PORT=3100 DEMO_PLATFORM_PORT=3101 npm run demo
```

## Настоящий локальный Moodle в Docker

Отдельный стенд **Moodle 5.3 + PostgreSQL 17** доступен на `http://localhost:8000`. Только два контейнера, постоянные тома, порт Moodle на loopback; PostgreSQL наружу не открыт. LTI, Cloudflare и Gnomio в этом шаге не подключаются.

После клонирования нужен Docker Desktop и Node.js 24+. Один сценарий создаёт приватную конфигурацию с отдельными случайными паролями, запускает сервисы и устанавливает Moodle:

```sh
make moodle-init
make moodle-status
```

Вход — `admin`, пароль из **локального** `.env.moodle`. Существующий файл не перезаписывается, пароль установленного администратора не меняется. Команды используют отдельный `compose.moodle.yaml`, не существующий Compose для MongoDB. Инструкция по установке, сохранению данных, ручному cron и проверкам — в [docs/local-moodle.md](docs/local-moodle.md). Пароли и содержимое томов в Git не включаются.

### Настоящее локальное подключение LTI 1.3

После установки Moodle:

```sh
make lti-local-init
make lti-local-start
# В другом терминале:
make lti-local-activate
make lti-local-status
```

Это обычный сервер с реальными MongoDB и Moodle, не демо. Подготовлены курс `RAG-LTI-LAB`, один LTI-элемент с максимумом 10 и два студента `lti_student_a` / `lti_student_b`. Пароли — в приватном `.env.lti-students`; сервер использует отдельный `.env.lti-local`. Повторная подготовка не сбрасывает данные или оценки.

Проверка **0 → 7 → 10 для обоих студентов** выполнена в настоящем Moodle, включая его журнал. На loopback используется поддерживаемый Moodle публичный RSA PEM-ключ, без отключения сетевых ограничений и проверки подписи. Это локальный HTTP-этап, не подтверждение публичного HTTPS-развёртывания. Команды, ссылки на курс, таблица результатов и снимки — в [docs/local-lti.md](docs/local-lti.md).

Итоговые оценки оставлены **А = 10 / Б = 7** в одной колонке. Отдельный преподаватель без прав администратора получил настоящую роль Instructor; девять живых проверок API подтвердили отказы 400/403 без изменения оценок и попыток. Для повторения: `make lti-local-instructor`, затем `make lti-local-verify`. [Итоговый протокол и скриншоты](docs/local-lti-final-checks.md).

## Обычный сервер для подключения Moodle

Обычный сервер использует MongoDB для платформы, ключей LTI и nonce; попытки хранятся отдельными JSON-файлами. MongoDB не является LRS.

```sh
make local-env
make mongo-up
make start
```

Docker нужен только для предложенного способа запуска MongoDB. Можно использовать установленную MongoDB, задав `MONGO_URL`; не запускайте второй сервер БД на занятом порту 27017.

До заполнения `MOODLE_*` [проверка состояния](http://127.0.0.1:3000/healthz) вернёт `{"ok":true,"configured":false}`. Учебные сессии и фиктивные оценки в таком режиме не создаются. Все шесть реквизитов Moodle задаются одновременно; частичная конфигурация отклоняется.

Для удалённой LMS потребуется доступный браузеру и серверу Moodle HTTPS-адрес: например, `https://trainer.example.org` или безопасная подпапка, без query string и фрагмента. `LISTEN_HOST=127.0.0.1` рассчитан на HTTPS reverse proxy на том же хосте. **Не публикуйте MongoDB, `data/` и исходники сервера как веб-файлы.** Подробная регистрация — в [docs/moodle-setup.md](docs/moodle-setup.md).

Публичный стенд без Cloudflare развёрнут на [Helios](https://se.ifmo.ru/~s507353/moodle-lti-rag/): PHP-шлюз → приватный Node.js → MongoDB через Unix-сокет. Поддержка подпапки не меняет форматы API или сохранённых попыток. Команды `make helios-*`, ограничения общего origin и регистрация Gnomio описаны в [docs/helios.md](docs/helios.md).

11.10.2026 инструмент зарегистрирован в настоящем Gnomio, в курс Test добавлен [элемент LTI](https://eoweblab.gnomio.com/mod/lti/view.php?id=6) с максимумом 10. Для вымышленного `student1` через штатное «Войти как» проверены 0 → 7 → 10 в одной и той же строке журнала; итог — 10. Затем пользователь самостоятельно вошёл как `student1`: новый запуск из курса восстановил 10/10 и историю 0/7, журнал подтвердил прежние 10.00 без новой попытки или отправки оценки. Второй вымышленный `student2` вошёл обычным способом: новая сессия ID 4 была пустой, пустые ответы дали 0/10, после обновления остались 0 и собственная пустая история предыдущих попыток. Grader report администратора подтвердил **student1 = 10 / student2 = 0** в общей колонке grade item ID 5; ручных исправлений нет. Администратор с ролью Teacher получает только просмотр. Отдельный неадминистративный Instructor и живые 400/403 именно в Gnomio пока не проверены; их настоящий локальный протокол сохранён отдельно. [Фактический протокол](docs/gnomio-lti-evidence.json) и [обычный вход A: результат и история](docs/screenshots/gnomio-student1-normal-login-app.jpg).

## Попытки, повтор и доставка

1. Сервер проверяет LTI-запуск: зарегистрированные issuer/client ID, точный deployment ID, ресурс и курс. Роль `Learner` разрешает отправку; преподаватель, смешанная роль и неизвестные роли — просмотр.
2. Браузер получает одноразовый билет (60 секунд), затем HttpOnly-сессию на 45 минут и CSRF-токен. JWT и `ltik` не передаются в URL приложения. Билет удаляется при использовании; переход на `/app` очищает URL. Proxy access log не должен сохранять query string маршрута `/session/start`.
3. `/api/submit` принимает только UUID v4 `requestId` и объект строк `answers`. Пользователь, баллы, максимум и адрес колонки определяются на сервере. Эталоны не отдаются в публичный API.
4. Попытка и возрастающий timestamp записываются на диск **до** OAuth/AGS. Используется только существующий `lineItemId` проверенного запуска, без создания новых колонок.
5. Повтор того же UUID с теми же строками возвращает сохранённый результат. После `sent` дополнительного AGS-вызова нет, даже для старого UUID из истории. Тот же UUID с другими ответами — HTTP 409. Регистр нормализуется при оценивании, а повторы сравниваются по исходным строкам.
6. При ошибке/таймауте — HTTP 502 с `{ok: false, current, error}`, `pending`; ответы заморожены. Это сохранённая попытка, а не потерянный результат. Явный повтор доставляет тот же результат. «Новая попытка» доступна только после `sent` и перемещает завершённую попытку в историю.

AGS получает `userId`, `scoreGiven`, `scoreMaximum: 10`, `activityProgress: Completed`, `gradingProgress: FullyGraded` и ISO timestamp. URL `.../scores` строит `ltijs` с сохранением query string Moodle.

Нельзя обещать exactly-once: Moodle мог принять оценку, а ответ потеряться. Тогда повтор может ещё раз записать **ту же** оценку. Сериализация и сохранённый возрастающий timestamp защищают порядок доставки; старый подтверждённый UUID не отправляется заново и не перезаписывает новую оценку.

История разделена по issuer, client ID, deployment ID, user ID, курсу и resource link. API возвращает всю историю в порядке создания, как стартер; UI показывает последние 20 предыдущих попыток, начиная с новых. Старые UUID остаются на диске для защиты от устаревших повторов. Передаётся последняя завершённая оценка, а не лучшая из попыток.

## Контракт API стартера

Маршруты приложения согласованы с `Moodle_LTI_Three_Tasks_Starter.zip` от 07.10.2026:

| Запрос                                      | Ответ                                                                                                                       |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/session`                          | 200; `label`, `userId`, `name`, `roles`, `course`, `resource`, `learner`, `agsReady`, `csrf`, `tasks`, `current`, `history` |
| `POST /api/submit`, доставка подтверждена   | 200; `{ok: true, current}`                                                                                                  |
| Повтор подтверждённого `requestId`          | 200; `{ok: true, duplicate: true, current}`, без нового AGS-вызова                                                          |
| `POST /api/submit`, AGS не подтвердил приём | 502; `{ok: false, current, error}`, попытка остаётся `pending`                                                              |
| `POST /api/new-attempt` с `{}`              | 200; `{ok: true}`; состояние обновляется через `/api/session`                                                               |
| Ошибка сессии / прав / валидации            | Соответствующий 4xx; читаемая строка `error` и дополнительный машинный `code`                                               |

Оба POST требуют действующую сессию, CSRF и **точное совпадение `Origin` с origin адреса `PUBLIC_URL`** (схема, хост и порт, без подпапки). Отсутствующий, пустой, `null` или чужой Origin отклоняется с 403 без изменения попыток и отправки AGS. Браузер выставляет Origin сам; подставлять его вручную в JS не нужно. Если есть `Sec-Fetch-Site`, он также должен быть `same-origin`. При подпапке ко всем маршрутам таблицы добавляется её префикс.

`current` и элементы `history` содержат поля попытки стартера: `id`, `requestId`, `answerSignature`, `answers`, `items`, `scoreGiven`, `scoreMaximum`, `createdAt`, `sentAt`, `status`, `lastDeliveryAt`. В существующем хранилище UUID запроса уже идентифицирует попытку, поэтому `id` равен `requestId`; `answerSignature` и `lastDeliveryAt` вычисляются из сохранённых ответов и timestamp. Формат JSON-файлов версии 1 не меняется, миграция не требуется. Приватный адрес `lineItemId` в API не включается.

Для расширенного интерфейса сохранены дополнительные поля сессии (`demo`, `courseTitle`, `resourceTitle`, `platform`, `gradeUnavailable`, `expiresAt`, `maxAnswerLength`, `scoreMaximum`, `historyTotal`) и попытки (`deliveries`, `lastError`). Это дополнения к полям стартера, а не переименования обязательных полей. Нормализация, UUID v4, строгая проверка ролей, сохранение перед AGS и защита архивных повторов остаются прежними.

Браузерный модуль `public/api.js` отличает 502 с сохранённым `current.status: pending` от обычной ошибки HTTP: первый позволяет показать результат и повтор доставки. Другие ошибки не скрываются; автоматической повторной отправки нет. Контрактные проверки находятся в `test/lti-integration.test.mjs`, клиентские — в `test/browser-api.test.mjs`.

## Ограничения учебного решения

- Один Node-процесс на `DATA_DIR`; операции одного ученика и ресурса сериализуются между всеми его сессиями. `.instance.lock` предотвращает одновременный второй процесс. Для нескольких инстансов нужны общее транзакционное хранилище и координация доставки.
- Сессии в памяти: после перезапуска/истечения 45 минут нужен повторный запуск из Moodle; попытки не теряются. Pending восстанавливается, повтор выполняется пользователем, фонового автоповтора нет.
- После аварийного завершения может остаться `.instance.lock`. Прочитайте записанный PID и убедитесь, что процесс завершён. Только после этого уберите **этот конкретный файл**; не удаляйте JSON попыток и `data/`.
- Для этого стенда AGS line item должен быть на том же origin, что Moodle issuer. Cross-origin AGS, Deep Linking и Submission Review не поддерживаются.
- Интерфейс открывается в **новом окне**, не iframe: CSP `frame-ancestors 'none'`. Inline JS разрешён только на OIDC-страницах библиотеки для state recovery; на `/app` запрещён. Блокирование localStorage может помешать входу — разрешите хранилище для origin инструмента.
- Перед использованием с реальными учениками настройте HTTPS, резервное копирование MongoDB и `data/`, доступ к серверу и сроки хранения учебных данных. Это учебный стенд, не сертифицированный или аудированный LTI-сервис.
