# Краткий план защиты лабораторной LTI

## Демонстрация на 5-7 минут

1. Открыть исходный LTI-элемент курса Test, а не прямой `/app`. Под student1 показать LTI ID 3, текущие 10/10 и собственные предыдущие 7/0.
2. В другой обычной сессии войти под student2. Показать LTI ID 4, текущие 0/10 и отсутствие истории student1. Не нажимать «Новая попытка», если нужно сохранить итоговые 10/0 для отчёта.
3. Под администратором открыть Grades -> Grader report: A=10, B=0 в одной колонке. Объяснить, что grade item ID 5 связан с одним resource link, а не создаётся после каждого ответа.
4. Показать `src/grading.mjs`: эталоны, веса 3/3/4, trim/lowercase, максимум 10. Показать, что браузер отправляет answers/requestId, но не userId, баллы или адрес AGS.
5. Запустить `npm test`; показать собственный тест INDEX -> 6/10 и проверки повторной доставки. Для управляемого сбоя использовать только `make demo`, явно назвать платформу имитационной.
6. Показать [протокол Gnomio](gnomio-lti-negative-evidence.json): отдельный instructor1, два 403 преподавателя и пять 400/403 student2, неизменные 10/0 и SHA-256 файлов. Для Instructor результат сообщён пользователем; для student2 сохранён полный JSON консоли. Локальный протокол содержит девять отказов, включая два случая Origin; эти два случая не выдавать за проверки Gnomio.

Обычные входы и пароли выполняет владелец аккаунтов. Не показывать `.env`, cookies, JWT, CSRF или приватные ключи при демонстрации.

## Ответы на основные вопросы

| Вопрос                                        | Краткий ответ                                                                                                                       |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Откуда берётся userId?                        | Из подписанного запуска Moodle после проверки ltijs. Браузер не выбирает владельца оценки.                                          |
| Почему баллы считает сервер?                  | Клиентский ввод можно подменить. Эталоны, максимум и результат должны определяться доверенным кодом.                                |
| Что такое line item?                          | Существующая колонка оценки, адрес которой Moodle передаёт в AGS claim запуска. Наш инструмент не создаёт новую колонку при ответе. |
| Почему Instructor не отправляет оценку?       | Его роль разрешает просмотр, но оба POST блокируются сервером. Отключённой кнопки недостаточно.                                     |
| Чем повтор отличается от новой попытки?       | Повтор использует прежний UUID и баллы; новая попытка разрешена после sent и получает новый UUID.                                   |
| Что делать после ошибки AGS?                  | Сохранённый pending не удалять. Исправить причину, затем повторить доставку того же результата.                                     |
| Можно ли обещать exactly-once?                | Нет: ответ может потеряться после принятия Moodle. Возможна повторная отправка той же оценки.                                       |
| Что происходит после перезапуска?             | Сессия в памяти пропадает; новый запуск из Moodle восстанавливает попытки с диска. Ключи платформы хранятся в MongoDB.              |
| Что является реальным доказательством оценки? | Запись в настоящем журнале Moodle; сообщение приложения само по себе недостаточно.                                                  |
| Зачем MongoDB, это LRS?                       | Она нужна адаптеру ltijs для LTI. Это не LRS и не xAPI-хранилище.                                                                   |

## Индивидуальное изменение одного правила

Это план демонстрации, а не уже выполненная правка. Работать в отдельной локальной копии, не менять публичные оценки 10/0.

Пример: разрешить для q2 дополнительный русский ответ `эмбеддинг`, сохранив `embedding` и веса 3/3/4.

1. До правки добавить в `test/grading.test.mjs` тест: rag / эмбеддинг / api должен давать 10/10. Убедиться, что он сейчас падает с 7/10.
2. В серверном определении q2 добавить разрешённый синоним; сравнение выполнять по нормализованным значениям. Список допустимых ответов не включать в getPublicTasks.
3. Изменить формулировку q2: «Введите английский термин в единственном числе или его русский эквивалент». Обновить docs/questions.md, чтобы инструкция не противоречила проверке.
4. Запустить npm test и make check-ci. Старые RAG / embedding / API по-прежнему дают 10; INDEX в q3 по-прежнему даёт 6; максимум остаётся 10; публичный DTO не раскрывает эталоны.
5. Показать правило в локальном make demo. Явно объяснить: старые сохранённые попытки автоматически не пересчитываются, а демонстрация не отправляет данные в Gnomio.

Если преподаватель предложит другое правило, сначала уточнить его ожидаемый результат и написать соответствующий тест. Не менять шкалу 3/3/4 или контракт q1/q2/q3 без отдельного требования.
